- 2026-10-10: A WSL shell saw a different terminal than cmd and PowerShell in the same window: native children had `TERM=xterm-ghostty`, `COLORTERM=truecolor`, `TERM_PROGRAM=ghostty` and `TERM_PROGRAM_VERSION`, bash in Ubuntu had `TERM=xterm-256color` and the other three unset, because `wsl.exe` hands a Linux process only what `WSLENV` lists and nothing in noctty listed anything. `termio/wsl_env.zig` now merges `COLORTERM`, `TERM_PROGRAM` and `TERM_PROGRAM_VERSION` into the child's `WSLENV` for a WSL launch, after the configured `env` overrides: the user's entries, flags and order stay, names are matched exactly (Linux names are case-sensitive), only names are added, and no path (`TERMINFO`) is ever exported. Each added name carries `/u`: without it a Windows program started from inside WSL gets the Linux value back (review measured `cmd.exe` from WSL printing `linux` for a plain `FOO` entry and `win` for `FOO/u`), for example `git.exe` under tmux receiving `TERM=tmux-256color`. A WSL launch is `isWslArgv` on the final argv, or the first word of a shell-form `command = wsl.exe ...`, which `execCommand` runs as `cmd.exe /C <line>` (the documented way to make WSL the default, and the first version missed it). `TERM` is listed only when the distribution has a terminfo entry for the configured `term`, asked of the distribution itself: `wsl.exe <-d/-u/--system/--distribution-id as launched> --exec infocmp <term>`, run in `Subprocess.start` (never `init`, which runs on the UI thread). The cache lock covers the table only and a tab waits on a pending probe of its own question alone, so one slow distribution does not hold every other WSL tab (or a tab close, which joins the thread). A `TERM` set through `env` is listed without a probe. - 2026-10-02: `'xterm-ghostty': unknown terminal type.` under `git diff` (#286) came from Git for Windows' ncurses, not from noctty's core: `GhosttyResources` skipped `tic` on Windows, so the package shipped only `share/terminfo/ghostty.terminfo` (source) and `less` (git's pager), `tput`, `vim` and `nano` had no compiled entry. `less` 704 calls `setupterm` without an error pointer, so ncurses prints the message and exits 1 and git shows nothing. The fix has two halves. (a) The Windows build compiles the entry itself (`src/terminfo/compiled.zig`, `ghostty-build-data +terminfo-database`) into `share/terminfo/78/xterm-ghostty` and `67/ghostty`, the hex layout that ncurses on MSYS2 and Cygwin reads (Git's ncurses 6.6.20251230 ignored a letter `x/` dir). The output is byte-identical (same SHA-256, same `infocmp -x`) to that `tic -x`, and three synthetic entries compiled by it are pinned as fixtures (canceled capabilities, `OT*` names past the SVr4 ones, every string escape, 32-bit numbers, every padding byte). tic writes booleans only up to the last TRUE one, so a canceled boolean never lengthens the section; Sourcery claimed otherwise and the third fixture shows it. (b) `App.init` installs that entry into `.terminfo` under the HOME Git for Windows gives its tools (`apprt/win32_terminfo.zig`), and TERMINFO is no longer exported on Windows. git.exe sets an unset HOME to HOMEDRIVE+HOMEPATH if that is a directory, else USERPROFILE (compat/mingw.c), but the MSYS2 runtime gives a directly started tool HOMEDRIVE+HOMEPATH unchecked: review measured that with HOMEDRIVE on a missing drive, a direct `tput` looked under `/q/...` while git's children used USERPROFILE. So the install, and the TERM check that runs after the configured `env` overrides against the child's HOME, use HOME, or HOMEDRIVE+HOMEPATH only when it is a local directory, or USERPROFILE only when neither is set; otherwise they give up and TERM falls back to `xterm-256color`. They also give up on a UNC or mapped network home (`GetDriveTypeW` reads the local drive table without contacting the server), because the check runs on the UI thread at startup and for every new terminal, where a disconnected share would block for a network timeout. Measured on a hidden desktop with HOME pointed at a scratch directory: git's pager, `less`, `vim` and `tput` found it from the install's drive, from a `subst` drive, and through Git Bash -> `cmd.exe` -> `less`. The install never replaces a file it did not write: it records the SHA-256 of what it installed in `.terminfo\.noctty-installed`, beside the entries so the record follows a roaming or shared home (a first draft kept it in LOCALAPPDATA, and review measured an entry stuck at its old version once that record was gone), and rewrites a file only while it holds that entry. It creates only `.terminfo` itself, never a missing home, and writes through an exclusively created, randomly named temporary file. It is skipped in portable mode, when `term` names another entry, and under `builtin.is_test`. `hasEntry` requires a whole compiled entry (every section its header declares), so an empty, foreign or cut-off file there also falls back. Why not TERMINFO, measured with release 1.3.131 and with review drafts of this fix: (1) That ncurses joins TERMINFO, `$HOME/.terminfo` and TERMINFO_DIRS and splits the result on `:`, so the old `TERMINFO=C:\...\share/terminfo` was searched as a directory `C` relative to the current directory, then as `\...\share\terminfo` on the current directory's drive. And with a compiled entry in place, `less` still failed whenever the current directory was on another drive. (2) No TERMINFO value is absolute to every reader. `/proc/cygdrive/c/...` is absolute to MSYS2 (and, by Cygwin's documentation, to Cygwin), but native Windows programs that honor TERMINFO (Neovim's unibilium asks the database before its built-in `ghostty` entry; Helix's termini; neo-blessed) resolve it against the root of the current drive, `C:\proc\...`, which any account can create (`icacls C:\` grants Authenticated Users `AD`). `/c/...` works only in MSYS2, `/cygdrive/c/...` only in Cygwin, `\\?\Volume{...}` gave `Invalid argument` in MSYS2, `\\?\` paths do not normalize the `/` native readers join with, and `\\localhost\C$` needs administrator rights. Two reviewers flagged the `/proc/cygdrive` draft and the user chose the per-user install over it. What the install leaves: standalone MSYS2 and Cygwin keep HOME in their own `/home` and still lack `xterm-ghostty`; WSL starts distributions with `xterm-256color` unless WSLENV lists TERM; and `ssh.exe` sends `TERM` unchanged, so a host without the entry still needs the `ssh-env`/`ssh-terminfo` features.
